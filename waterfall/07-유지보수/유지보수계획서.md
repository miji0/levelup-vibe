## 1. 유지보수 유형

| 유형 | LevelUp에서의 예 | 처리 방식 |
|------|------------------|-----------|
| 수정 | 출처 수집 실패, 연결 확인 오류, 로그인 실패, 메일 상태 오류 | 증상 기록 → 원인 확인 → `fix/<이름>` 브랜치와 PR |
| 적응 | Google OAuth·Gmail 정책 변경, Vercel·Neon 요금제·한도 변경, Node 24·Python 3.12·PostgreSQL 17·Next.js 16 업데이트, 의존성 보안 패치 | 월 1회 점검, 변경 시 테스트 후 PR |
| 완전 | 요청 한도 상향(FUP-001), 수집 시간대 조정(FUP-003), UX 개선(UX-LU-005·006), 새 출처 추가 | 소유자가 시점과 값을 정한 뒤 `feature/<이름>` 브랜치와 PR |

비율 목표는 두지 않는다. 시범 운영 첫 달은 **수정과 확인 위주**로 보고, 이후 완전·예방 비중을 소유자가 정한다.

## 2. 변경 절차

개인 프로젝트이므로 별도 CR 양식 대신 저장소의 절차를 쓴다.

### 2.1 흐름

1. 변경 필요를 [구현 진행 현황](../04-구현/구현진행현황.md)의 후속 항목(FUP-NNN)이나 [UX 검토서](../08-검토/UX검토서.md) 이슈로 기록한다.
2. 소유자가 시점과 값을 정한다(요청 한도·수집 시간처럼 확정 설계를 바꾸는 항목은 반드시 소유자 결정).
3. 브랜치 이름(`feature/<이름>`·`fix/<이름>`)과 커밋 메시지(Conventional Commits)를 **제안하고 승인**받은 뒤 작업한다(AGENTS.md).
4. PR을 만든다. 앱 코드·의존성·빌드·배포·CI 설정을 바꾸면 PR 전에 lint와 테스트(pytest, 웹 lint·tsc·vitest, 필요 시 E2E)를 통과시킨다. 문서만 바꾸면 `git diff --check`와 링크 확인으로 충분하다.
5. CI(`Foundation checks`)가 통과하면 소유자가 병합한다. **`main`에 직접 push하지 않는다.**
6. 병합 후 Vercel 운영 배포가 READY인지, 인증 없는 API 요청이 401인지 확인한다([배포 계획서 3.2](../06-배포/배포계획서.md#32-배포-후-스모크-확인-목록)).
7. 설계가 바뀌면 PRD·설계서·테스트케이스·[결과 보고서](../05-테스트/테스트결과보고서.md)를 함께 고친다.

### 2.2 영향 확인 체크

| 변경 대상 | 같이 확인할 곳 |
|-----------|----------------|
| 요청 한도 | `backend/src/levelup/api/tech.py`, API 설계서 요청 한도 표, `test_resolve_rate_limit_is_shared_with_registration` |
| 수집 시각(`vercel.json` schedules) | PRD 8.3, API·시스템 설계의 "매시" 문구, README·설정 화면 문구, 스케줄러 테스트 |
| DB 스키마 | `db/migrations`에 **새 번호 파일**만 추가(기존 파일 수정 금지), 운영 DB에 별도 적용, 백업 복원 테스트 |
| 환경 변수 | `backend/.env.example`, [배포 계획서 2.1](../06-배포/배포계획서.md#21-운영-환경-변수-production-전용), 운영 가이드 |
| 수집기·출처 | 저장해 둔 RSS/HTML fixture 테스트, SSRF 방어 테스트(39개) |
| 메일 | 발송 중복 방지·재시도 테스트, 가짜 Gmail 전송 테스트. 실발송 확인은 `MAIL_DELIVERY_ENABLED=true` 후 테스트 메일 |

### 2.3 승인 기준

- 소유자 1인이 승인한다. 승인 기록은 PR 병합으로 갈음한다.
- 보안(OAuth·토큰 암호화·SSRF)이나 메일 발송에 관한 변경은 병합 전 테스트 결과를 PR 본문에 적는다.

## 3. 서비스 목표 (SLA 대신)

외부 고객이 없으므로 계약형 SLA는 두지 않는다. 아래는 **제안 목표**이며 무료·개인 요금제 한계를 전제로 한다.

### 3.1 장애 등급과 대응 목표

| 등급 | 정의 | 대응 목표 | 예 |
|------|------|-----------|----|
| P1 | 사이트 전체 불능, 메일 오발송·중복, 비밀값 노출 | 확인 즉시(당일) 조치 | API 500, 같은 브리핑 두 번 발송, 연결 문자열 노출 |
| P2 | 핵심 기능 불능 | 1일 이내 | 로그인 실패, 스케줄 미실행, Gmail 연결 끊김 |
| P3 | 일부 기능·출처 문제 | 1주 이내 | 특정 출처 수집 실패 지속, 화면 문구 오류 |
| P4 | 개선 사항 | 소유자 일정 | UX 이슈, 문구 개선 |

대응 절차는 [운영 가이드 4장](../06-배포/운영가이드.md#4-장애-대응-runbook)을 따른다.

### 3.2 가용성

- 수치 목표(예: 99.9%)는 정하지 않는다. Vercel·Neon 무료 요금제가 가용성을 보장하지 않고, 사용자는 소유자 1명이다.
- 알림 체계가 없어 장애를 **소유자가 확인해야 안다.** 시범 운영 중 매일 점검하고, 이후 주기를 정한다([운영 가이드 7장](../06-배포/운영가이드.md#7-정기-점검)).
- 7일 시범 운영에서 수집 성공 횟수, 메일 상태, 오류 횟수를 기록해 현실적인 목표를 정한다.

### 3.3 한도 초과 시

Vercel·Neon 무료 한도를 넘기면 **유료 전환 없이** 수집 시간대·빈도·출처 수 등 정책을 별도로 검토한다(구현 진행 현황 배포 전 순서 6번). 유료 전환은 소유자가 별도로 결정한다.

### 4.1 해소 원칙

1. 새 기능을 추가할 때 같은 영역의 부채를 함께 처리한다.
2. 시범 운영 종료 때 대장을 재정렬한다.
3. 운영 위험(TD-010~012)은 기능 개선보다 먼저 닫는다: 실발송을 켜기 **전에** TD-012, 장기 운영 **전에** TD-011을 닫는다.

## 5. 인수인계 기록

개인 프로젝트이며 인계 대상은 소유자 본인이다. 다른 사람에게 넘길 때 이 장을 기준으로 한다.

### 5.1 시스템 구성

[운영 가이드 1장](../06-배포/운영가이드.md#1-시스템-개요) 참조. 웹(Next.js)과 API(FastAPI)가 Vercel 프로젝트 하나에서 돌고, 운영 DB는 Neon PostgreSQL 17, 백업은 GitHub Actions, 스케줄은 Vercel Schedules다.

### 5.2 계정과 접근 권한

비밀번호·키는 적지 않는다. 계정 보관 위치만 적는다.

| 서비스 | 대상 | 관리 |
|--------|------|------|
| GitHub | `miji0/levelup-vibe` | 소유자 |
| Vercel | 팀 `MJ`, 프로젝트 `levelup-vibe`(Hobby) | 소유자 |
| Neon | 운영 DB | 소유자 |
| Google Cloud | 프로젝트 `levelup-515910`, OAuth 웹 클라이언트 | 소유자 |
| 환경 변수·키 | Vercel Production에만 저장, 값은 소유자 별도 보관 | 소유자 |

### 5.3 정기 작업

[운영 가이드 7장](../06-배포/운영가이드.md#7-정기-점검)의 일일(시범 운영)·주간·월간 목록을 쓴다. 이 문서가 추가하는 것:

| 작업 | 주기 | 내용 |
|------|------|------|
| 의존성 점검 | 월 1회 | `uv`·`pnpm` 잠금 파일을 유지한 채 보안 업데이트 확인, 별도 PR |
| 런타임 버전 | 분기 | Node 24, Python 3.12, PostgreSQL 17 지원 종료 일정 확인 |
| 한도 점검 | 주 1회 | Vercel·Neon 사용량 |
| 비밀값 교체 | 노출 시 + 연 1회 검토 | 교체 순서는 운영 가이드 4.2 |
| 복원 훈련 | 첫 백업 직후 1회 + 분기 | 격리 DB에서 복원 |
| 테스트 공백 | 시범 운영 후 | TD-006 처리 여부 결정 |

### 5.4 알려진 이슈 목록

4장 대장과 [배포 계획서 G6 기록](../06-배포/배포계획서.md#7-g6-운영-인수-기록)의 남은 이슈를 합친 것이 현재 알려진 이슈 전체다. 새 이슈는 4장 표에 행을 추가한다.

### 5.5 연락처

개인 운영이므로 내부 연락처는 없다. 서비스 지원은 Vercel·Neon·GitHub·Google 각 대시보드의 지원 메뉴를 쓰며 무료 요금제는 지원이 제한된다.
