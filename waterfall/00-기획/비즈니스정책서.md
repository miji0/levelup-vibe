## 1. 문서 개요

### 1.1 목적

블로그 목록·이메일·설정·리포트 분석이 동일한 사용자 상태와 조건을 사용하도록 한다. 사이트 소유자는 범위와 예외를 검토하고, 구현 담당자와 Codex는 구체 규칙 ID를 기능·테스트에 연결한다. 별도 운영·QA 조직이 있다고 가정하지 않는다.

### 1.2 정책 작성 가이드

- 각 정책 분류는 목적·규칙·정상/경계/오류 예시·변경이력을 갖는다. 규칙의 근거는 PRD 장·MVP·AC에 연결한다.
- BP-AUTH는 분류이고 BP-AUTH-001은 실행 가능한 개별 규칙이다. 후속 SRS·유스케이스·RTM은 분류가 아니라 개별 ID를 참조한다.
- PRD에 없는 세부 동작은 아래 미결 참조에 명시한다. 미결은 구현자가 임의로 선택해도 된다는 뜻이 아니다.
- 기능 범위는 [PRD](../../PRD.md), 사용자 가치와 미결 결정의 원장은 [서비스 기획서 7.3](서비스기획서.md#73-가정의존성미결-결정), 시각적 근거는 [DESIGN.md](../../DESIGN.md)를 사용한다.
- 개인정보 처리·세션·삭제 기간 등 확인되지 않은 수치는 범용 예시에서 가져오지 않는다.

## 3. 인증/권한 정책

### 3.1 목적

소유자의 개인 구독·읽기 기록·설정을 보호하고 외부 AI 계정 접근과 사이트 인증을 분리한다.

### 3.2 규칙

| 규칙 ID | 규칙 | 근거·연결 |
|---------|------|-----------|
| BP-AUTH-001 | 개인 화면·데이터·설정은 인증된 소유자만 접근한다. 공개 회원가입과 다른 사용자 역할은 제공하지 않는다. 소유자 확인은 Google 로그인으로 확정한다. 검증한 Google sub가 구성된 소유자와 같고 email_verified=true여야 한다. 사이트 세션은 Google 로그인 성공 시점부터 7일(604,800초) 고정 만료다. 일반 요청·페이지 방문·cookie 재발급으로 최초 만료 시각을 연장하지 않는다. 만료 시 개인 API는 401로 응답하고 화면은 Google 로그인 후 안전한 원래 내부 경로로 복귀한다. 로그아웃은 즉시 세션을 종료한다. 사이트 세션 만료·로그아웃은 Gmail 발송 token이나 정기 작업을 해제하지 않는다. 세션은 무작위 cookie token과 서버 DB 저장으로 관리하고 로그아웃은 현재 세션만 폐기한다. 다른 기기의 유효 세션은 유지한다. DB 저장 세션의 고정 만료·폐기는 DEC-001의 실행 검증 대상이다 | PRD 2.1·8 / MVP-001 / AC-001 |
| BP-AUTH-002 | Gmail refresh token은 서버에서 암호화 보관하고 OAuth secret·암호화 키·DB 접속 정보는 저장소·클라이언트·일반 로그에 노출하지 않는다. Gmail 비밀번호·앱 비밀번호 입력란을 제공하지 않는다. ChatGPT·Claude 비밀번호·쿠키·API 키 입력란을 제공하지 않는다 | PRD 5.2·8 / MVP-001·008 |

### 3.3 예시

| 유형 | 관련 규칙 | 상황 | 결과 |
|------|-----------|------|------|
| 정상 | BP-AUTH-001 | 인증된 소유자가 구독 설정을 연다 | 개인 설정 조회·변경 허용 |
| 경계 | BP-AUTH-001 | 외부 원문 링크를 여는 경우 | 원문 사이트로 직접 이동. 원문 접근에 사이트 로그인 강제 없음 |
| 오류 | BP-AUTH-001·002 | 비소유자가 개인 데이터에 접근하거나 외부 AI 비밀번호 입력을 요구하는 흐름 | 개인 데이터 거절. 외부 계정 입력은 AI 서비스의 공식 화면에서만 수행 |

### 3.4 변경이력

현재 규칙은 해당 절의 규칙 표를 따른다.

## 4. 운영비용 정책

### 4.1 목적

개인용 서비스에 불필요한 결제 기능을 만들지 않고 사이트 운영비와 외부 AI 이용 조건을 구분한다.

### 4.2 규칙

| 규칙 ID | 규칙 | 근거·연결 |
|---------|------|-----------|
| BP-COST-001 | 첫 버전에는 사이트 결제·회원 등급·무료 체험·환불·광고·AI API 호출을 넣지 않는다. 운영비는 월 0원·무료 범위만 허용하며 자동 과금 전환·임의 데이터 삭제를 하지 않는다(PRD 8.3). 실제 무료 한도 검증은 DEC-001·002, 외부 AI 이용 조건은 소유자가 해당 서비스에서 확인한다 | PRD EX-001·006, 8장 / MVP-001·008 |

### 4.3 예시

| 유형 | 관련 규칙 | 상황 | 결과 |
|------|-----------|------|------|
| 정상 | BP-COST-001 | 리포트 분석에 진입한다 | 결제·API 키 요구 없이 요청문 준비 사용 |
| 경계 | BP-COST-001 | 외부 AI 서비스에서 사용 한도가 표시된다 | 사이트가 이용 한도·권한을 대신 부여하거나 무료 이용을 보장하지 않음 |
| 오류 | BP-COST-001 | 이메일 제공업체 제한으로 발송 실패 | BP-ERROR-003에 따라 실패 처리. 소유자에게 유료 회원 전환을 요구하지 않음 |

## 5. 콘텐츠 접근·수집 정책

### 5.1 목적

관심 기술 글을 빠짐없이 모으면서 초기 과거 글·중복·수정 글이 새 글 알림으로 섞이지 않게 한다.

### 5.2 규칙

| 규칙 ID | 규칙 | 근거·연결 |
|---------|------|-----------|
| BP-CONTENT-001 | 기본 제공 목록은 NAVER D2·카카오테크·우아한형제들·삼성SDS·SK플래닛 TECH TOPIC이며 수집 대상을 이 목록으로 제한하지 않는다. 구독한 공개 피드·목록이 제공하는 모든 새 글을 수집한다. 기술 글·채용·행사 모집·일반 기업 소식·기술 설명 없는 홍보를 모두 포함하고 유형으로 수집·목록·브리핑에서 자동 제외하지 않는다. 초기 과거 글·중복·구독·날짜·삭제 조건은 유지한다 | PRD 4.1 / MVP-002·003·004·005 / AC-020 |
| BP-CONTENT-002 | RSS·Atom 우선·매시 및 07:30 수집은 유지한다. 동일 ID/원문 URL은 기존 글을 재사용한다. 제목 수정은 재알림하지 않고, 게시일 정정은 pending 자격만 최신 값으로 재계산한다. 전체 응답 오류는 실패, 개별 필수 항목/식별 충돌은 격리하여 정상 항목은 partial로 처리한다 | PRD 4.1·4.2 / MVP-003 / AC-002 + CR-FLOW-001 |
| BP-CONTENT-003 | 처음 등록(first_add)의 최초 유효 기준 응답에 포함된 글은 baseline으로 제외한다. 그 뒤 늦게 발견한 과거 날짜 신규 글은 등록 시각 이전 게시라는 이유만으로 제외하지 않는다. 재구독(resume)/재추가(readd)는 새 기준 응답과 새 epoch 시작 전 게시 글을 제외한다. 기준 partial은 정상 항목 1개 이상일 때 완료 가능하며, 초기 격리 항목은 식별 가능하게 복구되면 baseline 제외를 유지한다. 기존 글/수동 상태는 보존한다 | PRD 4.1.1·4.2 / MVP-002·003 / AC-003·017·019 + CR-FLOW-001 |
| BP-CONTENT-004 | 구독을 켠 뒤 새로 발견한 해당 출처 글을 알림 후보로 삼는다. 해제한 출처의 글은 새 알림에서 제외하며 재구독 시 해제 기간 글을 소급 발송하지 않는다. 구독을 끄면 끄기 전에 발견한 글을 포함한 그 출처의 미요청 대기 알림을 모두 억제하며 재개 시 되살리지 않는다. 글·읽음·저장은 보존하고 새 epoch의 기준 수집부터 시작한다. 아직 외부 요청 전인 prepared에서 해당 글을 제외하되 sending/unknown/accepted는 변경하지 않는다 | PRD 4.2 / MVP-002·003 / AC-003 |

### 6.1 목적

## 7. 데이터 리셋/날짜 변경 정책

### 7.1 목적

한국 시간의 전날 글과 오늘 글을 구분하되, 날짜가 바뀌었다는 이유로 개인 상태와 발송 이력을 지우지 않는다.

### 7.2 규칙

| 규칙 ID | 규칙 | 근거·연결 |
|---------|------|-----------|

### 11.5 공통 UI·설정의 확장

일반 설정·연결 계정·기능별 설정으로 나눈다. 현재 알림 중지는 기술블로그 정기 메일만 대상으로 하고 테스트·수집·reports 사용은 기존 정책을 유지한다. 미래 기능의 알림·권한·저장·자동 요약은 실제 도입 때 별도로 설계한다. 콘텐츠 행은 배치 규칙만 공유하고 출처/발신자/매체 같은 metadata와 행동은 기능별로 구성한다. 계정 연결 해제와 개별 기능 중지의 영향을 구분해 안내하며 준비 기능을 위한 동의·토글은 만들지 않는다.

### 11.6 테마 선택·대비 정책 (CR-UX-002)

화면설계서 7.6의 테마 적용·저장·실패 처리 규칙을 따른다.

일반 텍스트는 4.5:1 이상, 조작 가능한 컨트롤/상태를 식별하는 필수 시각 정보는 인접색과 3:1 이상으로 검증한다. 꺼진 토글은 조작 가능하므로 비활성 컨트롤 면제로 취급하지 않는다. 장식 구분선과 실제 disabled 버튼의 예외는 UIX 7.6을 따른다. 색만으로 상태를 구분하지 않는다. 선택 저장 실패는 사이트 인증이나 업무 설정 실패와 구분한다.

### 11.7 수집·날짜·상태·스케줄 보완 (CR-FLOW-001)

CR-FLOW-001(2026-11-25): 소유자가 ① 첫 등록의 기준 수집 이후 늦은 발견 알림 허용, ② 대기 글의 최신 게시일 기준 재계산, ⑤ 실제 브리핑 시작 시 대상 확정·발송 우선·08:10 미시작 이월을 선택했다. ③ 날짜별 상태 조회, ④ 항목 격리·부분 성공, ⑥ 준비 카드 예외·참조 기준선은 본 검토 요청에 따른 설계 보완이다. 이 변경 범위만 반영하며 전체 G0~G4 승인·구현·실행 테스트 완료로 기록하지 않는다. 현재 시작 마감은 2026-11-26 사용자 결정에 따라 08:20으로 변경되었으며 PRD 4.4를 우선한다.

| 항목 | 결정·처리 | 보존·한계 |
|---|---|---|
| ① 첫 등록 / 재활성 구분 | first_add는 최초 유효 기준 응답의 글만 baseline으로 제외한다. 이후 늦게 발견한 과거 날짜 글은 후보다. resume/readd는 새 기준 응답 및 새 epoch 시작 전 게시 글을 제외한다 | 기존 baseline·suppressed·notified 글과 수동 상태는 되살리지 않음. 무게시일·식별 불가 항목의 과거 여부는 추정하지 않음 |
| ② 게시일 정정 | pending의 최신 게시일로 eligible_on을 재계산한다. 게시일 있음: max(게시 KST 날짜+1, 최초 발견 KST 날짜). 없음/무효: 최초 발견 KST 날짜+1 | prepared는 전송 직전 재검사·제외/새 revision. sending/unknown/accepted의 snapshot·예약은 보존하며 재알림하지 않음 |
| ③ 날짜별 상태 | 정기는 API-022 날짜별 브리핑 기준, 테스트는 API-015 발송 기록 기준. delivery 없는 날도 표시 | 미확정 건수는 null, 실제 snapshot의 빈 대상만 0. GET은 발송/수집/기록 생성 부작용 없음 |
| ④ 항목 오류 | 응답/문서 전체 오류는 실패. 유효 항목과 격리 항목이 섞이면 partial로 저장하고 정상 항목은 계속 처리 | 초기 partial은 유효 항목 1개 이상이면 기준 확정. 모든 항목 무효이면 기준 미완료. 정상 빈 피드는 완료 가능 |
| ⑤ 발송 시각 | KST [08:00,08:20) 안에 owner 잠금과 최초 snapshot을 확보한 실제 시작 시점으로 대상 확정. 수집 슬롯 완료를 기다리지 않음 | 08:20 정각까지 시작하지 못하면 missed. 다음 정상 아침에 유효 미발송을 합침. 이미 시작한 외부 요청의 늦은 결과는 계속 기록 |
| ⑥ 기준선 | 실행 메뉴에는 활성 기능만, 홈에는 지정 준비 카드 2개를 추가 허용. live 참조·변경 이력 동기화 | CR-UX-002 테마 결정·기존 개인 상태·발송 이력 유지 |

eligible_on은 예약 시각이 아니라 날짜상 최소 자격이다. 실제 작업의 단일 DB 읽기 snapshot에 보이는 글만 대상이며, 첫 확정 이후 새로 저장/자격 획득한 글은 다음 정상 아침에 처리한다. 08:03 수집 커밋→08:05 첫 확정이면 과거 게시 글은 당일 포함할 수 있다. 08:05 첫 확정→08:06 커밋이면 다음 날이다. 무게시일 글은 발견일 다음 날 규칙이 우선한다. 전송 전 게시일 정정·구독/연결 변경으로 기존 대상은 제거할 수 있지만 확정 이후 새 글을 같은 날짜 snapshot에 추가하지 않는다.

부분 기준 수집에서 격리한 항목의 출처 ID/URL hash가 복구 항목과 일치하면 최초 기준 항목으로 계속 제외한다. 안정 식별자가 없고 항목 내용까지 바뀌면 같은 글인지 보장할 수 없다. 이 경우 초기 수집에 없던 식별 불가/무게시일 글과 같은 관측 한계로 표시하며 임의 합병·과거 여부 추정을 하지 않는다. 자동 오류 항목 삭제/수동 재발송 기능은 추가하지 않는다.

### 13.1 정책 변경 프로세스

변경 요청 → 관련 MVP·EX·AC와 데이터·진행 중 발송 영향 검토 → 소유자 판단 → PRD·기획·정책 수정 → 관련 SRS·RTM·설계·테스트 연결 → 구현·검증 → 배포 판단·변경이력 기록 순으로 진행한다.

정책 적용일·시간대·소급 여부와 기존 발송 대기 건 처리 방식을 함께 기록한다. 담당 조직이나 CCB를 새로 만든다고 가정하지 않는다. 상세 변경 기록은 [변경 관리 계획](../08-검토/프로젝트관리-산출물.md#4-변경-관리-계획)의 양식을 필요 범위에서 사용한다.

### 13.2 정책 변경 시 확인 사항

아래는 향후 변경 검토 항목이며 현재 완료 표시가 아니다.

- [ ] 변경 이유와 근거, 관련 MVP·EX·AC·BP ID를 기록한다.
- [ ] 기존 구독·읽기·저장·미발송 브리핑에 대한 영향을 검토한다.
- [ ] 발송 경계·소급·재시도와 데이터 보존 처리를 결정한다.
- [ ] 서비스 기획서 DEC 원장의 미결 해소 상태를 갱신한다.
- [ ] 작성된 후속 FR·TC·RTM이 있으면 함께 갱신한다.
- [ ] 소유자의 실제 승인자·날짜·근거와 적용 시점을 기록한다.

## 부록

### A. 정책 ID 체계

BP-분류는 목차용이고 BP-분류-3자리번호는 구체 동작을 참조하는 ID다. 본 문서는 불필요한 다단계 ID를 추가하지 않는다. 규칙 표의 ID를 SRS·유스케이스·RTM에서 동일하게 사용한다.

### CR-MIN-001 최소 구현 기준

배포 구성·발송 최소화 범위는 서비스기획서의 CR-MIN-001 최소 구현 기준을 따른다.

첫 버전은 정기 브리핑 날짜당 외부 send 최대 1회다. 명확한 미접수는 예약을 해제하고 최신 게시일/epoch로 자격을 재계산해 다음 정상 아침에 합친다. unknown은 확인 전 held를 유지한다. 같은 날 새로운 revision으로 외부 send를 다시 호출하지 않는다. prepared revision은 첫 외부 호출 전 내용 정정에만 사용한다. 동일 테스트 요청 UUID도 외부 호출 1회이며 사용자의 새로운 테스트 조작은 새 UUID로 구분한다. 접수 후 DB receipt 기록 재시도는 외부 재발송과 구분한다.
