## 1. 시스템 개요

### 1.1 구성

```
브라우저 ──HTTPS──▶ Vercel (levelup-vibe.vercel.app)
                     ├─ web : Next.js 16 (화면)
                     └─ api : FastAPI (/api/*, 최대 300초)
                              ├─▶ Neon PostgreSQL 17 (직접 연결)
                              ├─▶ 기술 블로그 RSS/HTML (공개 주소, 수집)
                              └─▶ Google (로그인, Gmail 발송)
Vercel Schedules ──POST + Bearer CRON_SECRET──▶ /api/internal/schedules/*
GitHub Actions ──주 1회──▶ 암호화 DB 백업 (비공개 Artifact)
```

### 1.2 주요 구성요소

| 구성요소 | 역할 | 비고 |
|----------|------|------|
| web | 로그인, 구독, 읽기 목록, 브리핑, 설정, 리포트 인계 화면 | `apps/web` |
| api | 인증, 수집, 브리핑, 메일, 스케줄 진입점 | `backend/src/levelup` |
| DB | 소유자·세션·구독·글·수집 기록·메일 기록 | migration 001~003 |
| 스케줄러 | `hourly`, `final`, `digest` | 아래 6장 |
| 백업 | `backup.yml` | 비공개 저장소 필요 |

### 1.3 기술 스택

| 영역 | 기술 |
|------|------|
| 웹 | Next.js 16, TypeScript, pnpm, Node 24 |
| API | Python 3.12, FastAPI, SQLAlchemy(NullPool), uv |
| DB | PostgreSQL 17 |
| 테스트 | pytest, vitest, Playwright |
| 호스팅 | Vercel(Services + Schedules), Neon, GitHub Actions |

## 3. 모니터링

전용 모니터링 도구는 없다. 소유자가 아래를 직접 본다.

| 확인 | 방법 | 정상 |
|------|------|------|
| 배포 상태 | Vercel 프로젝트 → Deployments | 최신이 READY |
| API 오류 | Vercel → Logs(Runtime) | 5xx 없음 |
| 스케줄 실행 | 구독 화면 출처별 "마지막 성공" 시각이 정시 직후(최대 15분 지연)로 매시 갱신되는지. Vercel Logs는 출력이 있는 호출만 보여 보조로만 쓴다 | 매시 갱신 (2026-11-27 04:07 첫 확인) |
| 수집 상태 | 구독 화면의 출처별 상태 | 대부분 성공, 실패는 일시적 |
| 메일 상태 | 설정 화면 테스트 메일·Gmail 상태, 수집·발송 상태의 이메일 발송 기록 | 현재 발송이 켜져 있어 접수·도착(2026-11-27 15:45 테스트 메일 확인). `DELIVERY_DISABLED`가 나오면 환경 변수 확인 |
| DB 한도 | Neon 대시보드 | 무료 한도 이내 (**아직 확인 전**) |
| 백업 | GitHub → Actions → Encrypted weekly database backup | 주 1회 성공 (**설정 전**) |

자동 알림은 없다. 메일 발송이 실패하면 설정 화면의 상태로 확인한다.

## 4. 장애 대응 (Runbook)

### 4.1 증상별 대응

| 증상 | 가능한 원인 | 확인 | 조치 |
|------|------------|------|------|
| API가 500, 로그에 `Vercel requires an explicit HTTPS APP_ORIGIN` | `APP_ORIGIN` 등 환경 변수 누락 | Vercel → Settings → Environment Variables에서 이름 대조 | 누락 항목 추가 후 **Redeploy**(값 변경은 재배포해야 반영) |
| 로그인 화면에서 Google 오류(redirect_uri_mismatch) | 리디렉션 URI 불일치 | Google 콘솔의 URI 2개와 운영 주소 대조 | URI 수정(반영에 수 분~수 시간) |
| 로그인은 되는데 소유자가 거절됨 | `OWNER_GOOGLE_SUB` 값 불일치 | 로그인한 계정의 `sub`와 환경 변수 비교 | 값 수정 후 재배포 |
| 설정에서 Gmail이 "연결 필요" 또는 발송 실패 | 토큰 만료·권한 철회, 테스트 모드 7일 만료 | 설정 화면 상태 | [다시 연결]. 반복되면 OAuth 프로덕션 게시 확인([배포 계획서 6장](배포계획서.md#6-google-oauth-앱-프로덕션-게시)) |
| 테스트 메일 상태 `DELIVERY_DISABLED` | `MAIL_DELIVERY_ENABLED=false`(현재 운영은 `true`로 켜 둠) | 환경 변수 | 켜 둔 상태에서 나오면 값이 `true`인지 확인. 끄려면 `false`, 켜려면 `true`로 바꾸고 **재배포**해야 적용된다 |
| 출처 연결 확인 실패(502) | 사이트가 서버 요청을 막음(`HTTP_ERROR`), 연결 불가, 시간 초과 | 개발자 도구 Network의 응답 코드(현재 화면은 일반 문구만 보임, UX-LU-006) | 잠시 후 재시도. 계속되면 다른 공개 피드를 찾는다. **User-Agent 위장 같은 우회는 하지 않는다**(예: 우아한형제들) |
| 429 `RATE_LIMITED` | 분당 한도(연결 확인·등록 합계 5회 등) | 1분 대기 | 1분 뒤 다시. 한도 상향은 FUP-001 |
| 스케줄이 실행되지 않음 | Schedules 미등록, `CRON_SECRET` 불일치 | 구독 화면의 "마지막 성공"이 한 시간 넘게 그대로인지(대시보드 Settings에는 Schedules 메뉴가 보이지 않았다). 로그의 401은 출력이 있을 때만 보임 | 배포에 `vercel.json`이 포함됐는지, `CRON_SECRET` 설정 확인 후 재배포 |
| DB 연결 오류 | 접속 문자열 오류, `-pooler` 주소 사용, Neon 중지 | 로그의 DB 오류 | **직접 연결**(`-pooler` 없음), `postgresql+psycopg://…?sslmode=require` 형식인지 확인 |
| 같은 메일이 두 번 발송 | 발송 중복 방지 이상 | 설정·메일 기록 | 즉시 `MAIL_DELIVERY_ENABLED=false` 후 재배포하고 원인 확인 |

### 4.2 비밀값 노출

| 값 | 조치 |
|----|------|
| Neon 연결 문자열·비밀번호 | Neon에서 비밀번호 재설정 → Vercel `DATABASE_URL` 교체 → 재배포 |
| Google 클라이언트 비밀번호 | 콘솔에서 새 비밀번호 생성 → Vercel 교체 → 이전 것 사용 중지 |
| `TOKEN_ENCRYPTION_KEY` | 바꾸면 저장된 Gmail 토큰을 읽을 수 없으므로 교체 후 Gmail [다시 연결] |
| `CRON_SECRET` | 새 값 생성 → Vercel 교체 → 재배포(스케줄이 새 값을 쓰는지 로그 확인) |

노출 사고에서는 먼저 **새 값을 만든 뒤 교체**하고, 이전 값을 폐기한다. 채팅·저장소·스크린샷에 값을 남기지 않는다.

## 5. 백업과 복구

| 항목 | 내용 |
|------|------|
| 방식 | GitHub Actions `backup.yml`이 `pg_dump` 후 암호화(`.lup`)하고 비공개 Artifact로 업로드 |
| 주기·보관 | 매주 월요일 03:00 KST. 최대 400일, 검증을 통과한 최근 성공본 4개 유지. 실패하면 이전 성공본을 지우지 않음 |
| 실행 조건 | **비공개 저장소**이고 `BACKUP_ENABLED=true`(repository variable). 공개 저장소에서는 실행되지 않음 |
| 필요한 설정 | secrets `BACKUP_DATABASE_URL`(직접 연결), `BACKUP_ENCRYPTION_KEY`(토큰 암호화 키와 별도 32바이트 base64) |
| 현재 상태 | **미설정·미실행.** CI의 `pg_dump` 복원 테스트만 통과 |

### 5.1 복구 절차

README의 명령을 쓴다. **운영 DB에 바로 복원하지 않는다.**

```sh
cd backend
uv run python -m levelup.backup verify <백업파일>.lup
# RESTORE_DATABASE_URL은 별도의 비어 있는 격리 DB여야 한다
uv run python -m levelup.backup restore <백업파일>.lup --isolated-target
```

1. 복원 중에는 `MAIL_DELIVERY_ENABLED=false`와 Schedules 비활성 상태를 유지한다.
2. 복원 결과를 확인한 뒤에만 운영 전환한다.
   복원 CLI는 기존 사이트 로그인 세션을 폐기한다. 이전 쿠키는 401이어야 하고 다시 로그인해야 한다. 세션 폐기 오류로 종료했다면 복원 완료로 간주하지 않고 격리 상태에서 해결한다. 글·읽음/저장·발송 이력은 보존한다([검증 기록](../05-테스트/테스트결과보고서.md#10-오류-수정-에이전트-보완-결과-2026-11-27)).
3. 마지막 백업 이후 접수된 메일은 백업에 없을 수 있으므로, 소유자가 Gmail의 Message-ID와 대조해 누락을 반영한다. **복원만으로 발송을 자동 재개하지 않는다.**

### 5.2 복구 훈련

첫 백업이 올라오면 격리 DB에 복원해 보는 훈련을 **한 번** 실시하고 결과를 [테스트 결과 보고서](../05-테스트/테스트결과보고서.md)에 남긴다. 이후 분기마다 반복한다.

## 6. 스케줄과 수집

| 이름 | 시각(KST) | 경로 | 하는 일 |
|------|-----------|------|---------|
| `hourly` | 매시 정각 | `/api/internal/schedules/hourly` | 활성 출처를 대기열에 넣고, 메일 작업을 처리하고, 약 210초 안에서 출처 2곳씩 동시에 수집 |
| `final` | 07:30 | `/api/internal/schedules/final` | 브리핑 직전 마지막 수집 |
| `digest` | 08:00 | `/api/internal/schedules/digest` | 아침 브리핑 메일 |

- Hobby 요금제는 정시 후 최대 약 15분 늦게 실행될 수 있다.
- 호출은 POST이며 `Authorization: Bearer <CRON_SECRET>`가 없으면 401이다.
- 메일은 `MAIL_DELIVERY_ENABLED=true`일 때만 나간다.
- **알려진 동작:** 출처를 추가한 시점부터 **첫 수집 전까지** 올라온 글은 기준(과거) 글로 기록돼 목록에는 보이지만 이메일에서는 빠진다. 새 출처는 되도록 업무 시간(수집 직전)에 추가한다.
- 수집 시간대 축소(FUP-003)와 요청 한도(FUP-001)는 [구현 진행 현황](../04-구현/구현진행현황.md)의 후속 항목이다.

## 2026-11-27 기능 연결 및 운영 기반 보완

현재 구현 범위·검증·배포 전 순서는 [구현 진행 현황](../04-구현/구현진행현황.md)을 참조한다. 비공개 Artifact 최대 400일·최근 성공본 4개 정책을 사용자가 확정했다. 로컬 구현/테스트와 실제 클라우드 실행·운영 인수를 구분한다. 기존 기록의 미구현 표시는 해당 시점의 상태이며 새 현황을 우선한다.
