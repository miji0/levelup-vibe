# LevelUp 에이전트 운영

## 공통 작업 규칙

모든 역할은 작업 전에 이 파일, 루트 `AGENTS.md`, 담당 경로의 하위 `AGENTS.md`를 읽는다. 답변은 한국어로 작성한다.

- 현재 코드와 관련 PRD·승인 기록을 확인하고, 할당된 목표와 검증 기준을 먼저 정한다. 과거 문서의 미구현 표현이나 통과 수를 현재 상태로 간주하지 않는다.
- 여러 에이전트가 같은 저장소에서 작업한다. 다른 담당의 변경을 되돌리지 않고 현재 변경에 맞춰 작업한다.
- 아래 담당 범위는 협업 지침이며 파일 접근 권한을 강제하는 장치는 아니다. 수정은 담당 범위 안에서 작업 지시로 지정된 파일에 한정한다. 경계 밖 변경은 총괄에게 요청하고 독립 작업을 계속한다.
- 공유 API·잠금·알림 자격·테스트 도우미를 바꾸면 호출부와 담당자에게 미치는 영향을 보고한다. 같은 파일에 두 수정 담당을 배정하지 않는다.
- 실제 오류를 수정할 때 재현 테스트를 먼저 확보한다. 검사 명령은 `README.md`와 도구 설정을 확인해 선택하고, 실행 명령·통과·실패·건너뜀을 구분한다. DB 검사에는 `TEST_DATABASE_URL`을 사용한다.
- 운영 발송·설정 변경·복원·배포는 해당 작업에 대한 사용자 승인 범위가 있을 때만 수행한다. 로컬 검사와 격리 환경 준비는 계속 진행한다. 비밀값은 출력하거나 기록하지 않는다.
- 브랜치·커밋·push는 총괄이 루트 `AGENTS.md`의 승인 규칙에 따라 처리한다. 사용자 승인과 출시 인수 판정을 에이전트가 대신하지 않는다.
- 최종 인계에는 변경 파일, 해결한 동작, 검사 결과, 미검증·차단 범위, 다른 담당에게 필요한 변경을 적는다. 구현 담당은 수정 코드와 별개로 문서에 반영할 근거를 총괄에게 전달한다.

## 역할과 소유권

| 이름 | 역할 | 수정 범위 |
| --- | --- | --- |
| `service-coordinator` | 계획·위임·통합·기록 | 아래 공유 파일, `waterfall/`, 루트 문서, `.codex/` |
| `frontend-ux` | 화면·상호작용·디자인 검증 | `apps/web/src/`, `apps/web/public/`, `tests/e2e/`, `apps/web/playwright.config.ts` |
| `collection-data` | 출처·수집·읽기 상태·정합성 | 수집 및 읽기 모듈과 관련 테스트(역할 TOML에 명시) |
| `briefing-gmail` | 브리핑·발송·스케줄 | 메일 및 스케줄 모듈과 관련 테스트(역할 TOML에 명시) |
| `security-ops` | 인증·외부 요청·배포·복구 | 보안·인프라·백업 및 CI 설정과 관련 테스트(역할 TOML에 명시) |
| `error-fixer` | 보고된 결함 재현·최소 수정·회귀 검증 | 총괄이 결함 ID별로 명시 배정한 파일만 수정. 전문 담당과 동일 파일 동시 수정 금지 |
| `qa-reviewer` | AC·TC·실행 근거 독립 검토 | 읽기 전용 지침. 코드·테스트·문서를 수정하지 않음 |

공유 파일은 `backend/src/levelup/api/{app,tech,inputs,errors}.py`, `backend/tests/{conftest,test_tech_api,e2e_server}.py`, `backend/src/levelup/migrate.py`, `db/migrations/`, 양쪽 의존성·잠금파일과 나머지 빌드·도구 설정이다. 총괄이 단독 통합하거나 작업 시작 전에 특정 담당 한 명에게 명시적으로 배정한다. 기존 SQL 마이그레이션은 보존하고 새 변경은 새 파일로 추가한다.

특히 `persistence.py`와 `eligibility.py`는 수집 담당, `scheduler.py`는 Gmail 담당이 수정한다. 메일의 잠금·임대·대상 자격에 영향이 있으면 양쪽 회귀 검사를 수행한다. 백엔드 테스트 사이의 도우미 import도 공유 계약으로 다룬다.

## 실행 순서

1. 총괄이 QA에 현재 AC별 검증 공백을 읽기 전용으로 확인시킨다.
2. 총괄이 우선순위·파일 소유권·완료 기준을 지정해 필요한 구현 담당을 배정한다. 가용 동시 실행 수 안에서 겹치지 않는 작업만 병렬로 진행한다.
3. 구현 담당은 수정과 관련 검사를 끝내고 근거를 인계한다. 운영 증빙이 필요한 작업은 보안·운영 담당과 협력한다.
4. QA가 최종 변경과 실행 근거를 독립 검토한다. 총괄이 잔여 문제를 해결하고 관련 검사를 재실행한다.
5. 총괄이 구현·테스트·UX 기록을 갱신하고, 완료 범위와 남은 제약을 사용자에게 보고한다. 승인된 마일스톤이 완료되면 커밋 지점을 알린다.

화면은 Figma 읽기 전용 대조 → 차이 수정 → 다크/라이트 × 1280px/390px 검증을 거친다. 참조·캡처·차이·검사 결과가 없으면 디자인 미검증으로 인계한다. 실제 Safari·Google·Gmail 확인을 모의 테스트로 대체하지 않는다.

## 요청 예시

> service-coordinator 기준으로 서비스 완성도를 점검해줘. qa-reviewer로 검증 공백을 먼저 확인한 뒤 필요한 담당에게 파일을 나눠 맡기고, 수정·검사·독립 QA까지 진행해줘. 운영 변경은 별도로 요청한 범위만 수행해줘.

> error-fixer로 테스트 결과 보고서의 지정한 결함을 수정해줘. 결함별 파일 소유권을 나눠 재현 테스트의 실패·수정 후 통과를 확인하고, qa-reviewer 검토 후 보고서에 보완 결과를 반영해줘.

각 TOML은 프로젝트용 커스텀 에이전트 정의다. 현재 세션의 도구가 해당 역할을 아직 표시하지 않으면 새 세션에서 확인한다. 현재 작업을 계속해야 할 때는 해당 TOML과 이 문서의 지침을 일반 서브에이전트의 작업 지시에 포함하고, 커스텀 역할로 실행된 것처럼 보고하지 않는다.

정의 형식과 권한 상속은 [공식 서브에이전트 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents)를 따른다. 모델과 추론 강도는 기존 QA 설정 외에는 지정하지 않는다. 파일 소유권과 QA 읽기 전용은 행동 지침이며 별도 샌드박스가 아니다.
